# jsdata

Extract JavaScript declarations from source files into a single generated ES module.

`jsdata` reads a small line-based config, pulls named `const` declarations **verbatim** out of
your real source files, and writes them into one `_wikiData.js` module. Nothing is re-serialised
or re-formatted — the text between `=` and the end of the declaration is copied as-is, so
comments, template literals, trailing commas and computed expressions all survive intact.

It exists so a documentation site can read an addon's real values instead of a hand-maintained
copy that silently drifts. It also understands [Vertion](https://github.com/vertX-dev/vertion)
version markers, so one source tree can produce a different module per released version.

```
src/BP/scripts/passives.js          jsdata.cfg                  src/wiki/_wikiData.js
────────────────────────────        ─────────────────────       ─────────────────────────────
export const PASSIVES = {           out src/wiki/_wikiData.js   // @generated by jsdata
  regen: { cost: 1 },         ──►   var PASSIVES =        ──►   export const PASSIVES = {
  haste: { cost: 2 },                 src/BP/scripts/             regen: { cost: 1 },
};                                    passives.js                 haste: { cost: 2 },
                                      -> const PASSIVES         };
```

## Install

Not published yet. Build from source:

```bash
cargo install --path .
```

## Quick start

Create a `jsdata.cfg` next to your project:

```
out src/wiki/_wikiData.js

var PASSIVES = src/BP/scripts/passives.js -> const PASSIVES
var RARITY   = src/BP/scripts/rarity.js   -> const RARITY
let PASSIVE_COUNT = Object.keys(PASSIVES).length
```

Then run `jsdata` in that folder. It writes:

```js
// @generated by jsdata - do not edit.
// config: jsdata.cfg
// built: 2026-09-04T07:07:27Z

export const PASSIVES = { regen: { cost: 1 }, haste: { cost: 2 } };
export const RARITY = { ... };
export const PASSIVE_COUNT = Object.keys(PASSIVES).length;
```

The file is only rewritten when something other than the timestamp changed, so watch mode
doesn't trigger pointless downstream rebuilds.

## Config reference

The grammar is strictly line-based — one directive per line, no multiline, no escaping.
Blank lines and lines starting with `#` are ignored. All paths resolve against the **config
file's own directory**, not the working directory.

### `out PATH`

Where to write the generated module. Optional; defaults to `_wikiData.js` next to the config.

### `var NAME = PATH -> const DECL`

Extract `const DECL` from `PATH` and export it as `NAME`. `export const DECL` is accepted too.
The line is split on the **last** `->`, so paths containing `->` still work.

```
var PASSIVES = src/BP/scripts/passives.js -> const PASSIVES
var TOOLS    = src/BP/scripts/tools.js    -> export const TOOLS_VANILLA
```

Only top-level declarations are found, and only the first binding of a
`const A = 1, B = 2` list.

### `let NAME = EXPR`

Emit a JavaScript expression verbatim, with no source file involved. Useful for values derived
from the extracted ones:

```
let PASSIVE_COUNT = Object.keys(PASSIVES).length
```

Entries are emitted in config order, so an expression may only reference names declared
**above** it. Referencing a later one is a temporal-dead-zone error at module load; `jsdata`
warns about it at build time instead.

### `langs <-- TEXTS_DIR <-- languages.json`

Read every locale listed in `languages.json`, load the matching `<locale>.lang` file from
`TEXTS_DIR`, and export the whole set as `langs`:

```js
export const langs = { en_US: { "item.foo.name": "Foo" }, de_DE: { ... } };
```

Always exported under the name `langs`, so there can be only one per config. A listed locale
with no `.lang` file is warned about and skipped rather than failing the build.

### `md NAME <-- FILE [<-- html]`

Export a markdown file as a JS string — verbatim, or converted to HTML with `<-- html`:

```
md CHANGELOG <-- changelog.md <-- html
```

> **Note:** HTML conversion does **not** sanitise. Raw HTML in the markdown passes straight
> through. That is fine for files you wrote; do not point it at contributor-submitted content.

### Path expansion

Paths may use `~`, `%VAR%`, `$VAR`, `${VAR}` and `${VAR:-fallback}`. The fallback form is what
lets one config serve both a plain checkout and a Vertion build:

```
var PASSIVES = ${VERTION_OUTPUT:-./src}/BP/scripts/passives.js -> const PASSIVES
```

That reads the freshly built, already version-filtered tree when run from a `vertion build`,
and `./src` when run by hand. An expanded absolute path replaces the config's directory.

## Version filtering

If your sources carry Vertion `//version` markers, `jsdata` can extract "as of" a given
version. It reuses Vertion's filter directly rather than parsing markers itself.

A spec is either cumulative or a range:

| Spec | Meaning |
|---|---|
| `2.1` | base content plus everything up to and including 2.1 |
| `2.1 2.3` | base content plus 2.1 through 2.3 |

Set it globally in the config, or pin one directive with a trailing ` --- ` suffix:

```
version = 2.5
versionTags = [beta]

var PASSIVES = src/BP/scripts/passives.js -> const PASSIVES
var LEGACY   = src/BP/scripts/legacy.js   -> const LEGACY   --- 2.0
var UI       = src/BP/scripts/ui.js       -> const UI       --- 2.5 [ui]
```

Precedence, highest first: a directive's `--- ` pin → the `--version` / `--tag` flags → the
config's `version` / `versionTags` → unfiltered.

The version and the tags resolve **independently**, so `--- 2.0` still inherits the surrounding
tag filter.

**Tags are opt-in**, exactly as in Vertion: a tagged block ships only when one of its tags is
active, so with no tag filter at all every *tagged* block is skipped. Untagged blocks are never
affected. `*` is the wildcard that admits every tag.

| Tag filter | Effect |
|---|---|
| none | untagged content only — every tagged block is skipped |
| `[beta]` | untagged content plus blocks tagged `beta` |
| `[*]` | everything, whatever its tags |
| `[]` | explicitly no tags active — use it to override an inherited `versionTags` |

This matters because it keeps the generated module consistent with the build: `jsdata --tag beta`
sees exactly what `vertion build --tag beta` shipped.

When one file declares the same `const` several times behind different markers, `jsdata` picks
the newest declaration that survives the filter. If every declaration is gated out, the entry is
skipped with a warning — along with any `let` that referenced it, so the emitted module never
references a name that isn't there. A declaration that appears at *no* version is a hard error,
since that is a typo rather than a version gap.

## Merge mode

`--pull-all` aggregates several projects into one namespaced module — this is how a wiki covering
many addons gets a single data file. It takes a different config shape:

```
out src/data/wikidata.js

vars RarityStats <-- W:/ADDONS/RarityStats <-- jsdata.cfg --- 2.0.1
vars CommandsPP  <-- W:/ADDONS/Commands++  <-- jsdata.cfg --- 2.0.0
vars Legacy      <-- W:/ADDONS/Legacy      --> _wikiData.js
langs <-- RP/texts <-- RP/texts/languages.json
```

- `<-- CONFIG` rebuilds that project from its own config, in memory, at the pinned version.
- `--> FILE` pulls an already-generated module verbatim. It cannot take a `--- ` pin, because
  a built file has no markers left to filter.

Each project becomes one export whose value is an IIFE, so intra-project references still
resolve:

```js
export const RarityStats = (() => {
  const PASSIVES = { ... };
  const PASSIVE_COUNT = Object.keys(PASSIVES).length;
  return { PASSIVES, PASSIVE_COUNT };
})();
```

## CLI

```
jsdata [OPTIONS] [CONFIG]
```

With no `CONFIG`, it uses `./jsdata.cfg`, then searches parent directories for the nearest one —
which is what lets a Vertion `run` line just say `jsdata` even though the build runs with its
working directory set to the output folder. Paths inside the config still resolve against the
config's own directory, so `out` keeps landing in the project.

| Flag | Effect |
|---|---|
| `--check` | Validate only; write nothing |
| `--pull` | Build once (the explicit form of a bare invocation) |
| `--pull-all` | Merge mode, see above |
| `--watch` | Rebuild when the config or any referenced source changes |
| `--structure` | Print what the config yields — every entry, its value shape, and for a multiply-declared `const`, each version found and which one this run selects |
| `--version SPEC` | Extract as of a version |
| `-t`, `--tag TAG` | Activate a tag. Repeatable; comma-separated values are split. Tags are opt-in — with none given, every tagged block is skipped. Pass `*` for all |

> **`--version` does not print the tool's version.** It means "extract as of this game version",
> which is the whole point of the flag for a Vertion `run` line. Use `--help` for the version.

An unexpanded `%VAR%` or `$VAR` passed to `--tag` is dropped with a warning rather than silently
filtering every block away — on Windows, `cmd` leaves `%VERTION_TAGS%` standing when the variable
is empty.

## Vertion interop

From a `vertion.cfg` `run` line:

```
"jsdata --version %VERTION_VERSION% --tag %VERTION_TAGS%",
```

Two setups are coherent, and mixing them is not:

- **Follow the build** — point sources at `$VERTION_OUTPUT` and use no `--- ` pins. The tree is
  already filtered.
- **Multi-version wiki** — point sources at the unfiltered `./src` and keep the pins.

Pinning a source that lives inside the build output can only narrow what the build already
dropped, so `jsdata` warns when it sees that combination.

## Editor support

`extension/` holds a VS Code extension: <kbd>Ctrl</kbd>+<kbd>Alt</kbd>+<kbd>W</kbd> appends a
`var` line for the declaration under the cursor, and tracked declarations get an inline marker.
It reads `jsdata.cfg` from the workspace root. Not published to the Marketplace yet — build it
with `npm install && npm run compile` in `extension/`.
